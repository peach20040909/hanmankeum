# AI 리터러시 디벨롭 설계 (초안)

작성 2026-10-30 · 승인 전 문서. 구현은 승인 후 시작한다.

## 왜 이걸 하나

대회 취지가 'AI 리터러시'다. 지금 한만큼은 **AI가 기록을 분류하고 요약하는 도구**다.
여기서 한 발 더 가면 **학생이 AI를 검증하는 과정 자체를 기록하고, 교수가 그 과정을 보는 도구**가 된다.

핵심 주장 한 줄:
> AI가 판단하지 않는다. 학생이 AI를 검증한 흔적이 남고, 교수는 결과가 아니라 그 과정을 본다.

이건 경쟁사(FeedbackFruits, LMS 내장 상호평가, GitHub Insights)가 하지 않는 영역이다.

## 지금 있는 것 (이미 구현됨)

| 장치 | 위치 | 동작 |
|---|---|---|
| 분류 교차 확인 | `collect.js` `needsReview` | AI 분류와 규칙 분류가 다르면 '확인 필요'로 표시, 교수가 확인해야 해제 |
| AI 사용 표시 | `collect.js` `detectAI` + 작성자 자가 표시 | 기록에 AI 도움 여부와 근거 문구 저장 |
| 근거 검증 | `generate.js` `validateSentences` | AI 문장의 인용 번호를 서버가 검증, 없는 번호·판단 표현은 문장째 제외 |
| 약한 연결 표시 | `generate.js` `overlap` | 인용 기록과 내용이 동떨어지면 `weak` 표시 |
| 이의 제기 | `POST /summary/objection` | 학생이 요약 문장별로 이의를 남기면 교수 리포트에 함께 보임 |
| 초안 수정률 | `generate.js` `compareDraft` | AI 초안 대비 유지·수정·추가·삭제 문장 수와 전체 수정률(%) |

**빠진 것**: 이 데이터가 흩어져 있고, 화면에서 "이 팀이 AI를 어떻게 썼는가"를 한눈에 못 본다.
학생이 문장을 **하나씩** 확인하는 흐름도 없다(지금은 체크박스 1개로 전체 확인).

## 만들 것 (3가지)

### 1. AI 리터러시 리포트 (교수 화면, 마감 후)

기여도 리포트 옆에 탭 하나. 팀 전체와 학생별로 **AI를 어떻게 다뤘는지**를 보여준다.

| 지표 | 계산 | 읽는 법 |
|---|---|---|
| 초안 수정률 | `statements.draft_diff.changed` | 0%면 AI 초안을 그대로 냈다는 뜻 |
| 문장별 확인 | 새 데이터 (아래 2번) | 몇 문장을 열어보고 확인했는가 |
| 이의 제기 | `summaries.sentences[].objection` 개수 | AI 결과를 그대로 받아들이지 않은 횟수 |
| AI 도움 표시 | `records.ai_assisted` 비율 | 스스로 밝힌 AI 사용 |
| 검증 탈락 문장 | `summaries.dropped` | AI가 만들었지만 근거가 없어 버린 문장 수 |

**숫자로 등수를 매기지 않는다.** "이 학생은 AI 초안을 0% 고쳤습니다" 같은 사실만 보여주고, 해석은 교수가 한다.
(기여율과 같은 원칙 — 판정하지 않고 근거를 제공한다.)

### 2. 문장별 근거 확인 흐름 (학생 화면, 자기 기술 작성 시)

지금: AI 초안 전체에 체크박스 1개 → 형식적 확인이 된다.
바꿀 것: 문장마다 ① 인용된 기록 보기 ② 맞음 / 고침 / 지움 선택.

- 각 문장 옆에 근거 기록 제목이 보이고, 누르면 원본(커밋·문서)으로 바로 간다.
- `weak` 표시가 붙은 문장은 "이 문장은 근거와 연결이 약합니다. 확인해 주세요"로 먼저 띄운다.
- 모든 문장을 처리해야 제출 버튼이 열린다.
- 처리 결과(확인/수정/삭제 수)가 1번 리포트로 간다.

이게 리터러시 훈련의 핵심이다. **AI 출력을 원본과 대조하는 행동을 UI가 강제한다.**

### 3. AI 사용 성찰 3문항 (학생 화면, 마감 후 1회)

자기 기술 제출 화면 아래 짧은 3문항. 선택 입력, 교수 리포트에 그대로 전달.

1. 이번 프로젝트에서 AI를 어디에 썼나요? (안 썼으면 '안 씀')
2. AI가 틀리거나 어색했던 부분이 있었나요?
3. 그걸 어떻게 확인하거나 고쳤나요?

점수화하지 않는다. 2·3번이 비어 있으면 교수 화면에 "검증 서술 없음"으로만 표시한다.

## 하지 않을 것 (non-goals)

- AI 사용량을 점수로 환산하는 것 — 기여율과 섞이면 "AI 많이 쓰면 손해" 신호가 된다
- AI 생성물 탐지(AI 탐지기) — 오탐이 많고, 우리 주장(판정하지 않는다)과 충돌
- 학생 간 AI 사용 비교·순위
- 프롬프트 전문 공개 — 운영 노하우라 버전 번호만 노출

## 실패 기준 (anti-goals)

- 학생이 문장 확인을 '클릭 노동'으로 느끼면 실패다. 문장 5개 이하, 1분 안에 끝나야 한다.
- 교수가 리포트에서 "그래서 뭘 보라는 거지?"라고 느끼면 실패다. 지표마다 한 줄 해석 문구가 붙어야 한다.

## 데이터 변경

```
statements 테이블
+ sentence_checks TEXT   -- [{i, action:'keep'|'edit'|'drop', opened:bool}]
+ reflection TEXT        -- {used, wrong, fixed}
```
기존 컬럼은 그대로 둔다. 마이그레이션은 `db.js`의 `COLUMNS` 배열에 2줄 추가.

## 구현 순서

1. 문장별 확인 흐름 (2번) — 데이터가 여기서 나온다
2. 성찰 3문항 (3번) — 간단
3. AI 리터러시 리포트 (1번) — 1·2의 데이터를 모아 보여줌
4. 시연 영상·발표 자료 갱신

테스트: 문장별 확인 없이 제출 시 400, 성찰 저장·조회, 리포트 지표 계산 3가지를 `api.test.js`에 추가.

## 정해야 할 것 (사장님 결정)

1. **발표에서 어느 쪽을 앞세울까** — "AI를 검증하는 과정을 기록한다"(리터러시) vs "기여를 근거와 함께 본다"(공정성). 둘 다 넣되 순서를 정해야 한다.
2. **문장별 확인을 필수로 할까, 권장으로 할까** — 필수면 데이터가 확실하지만 학생이 번거롭다.
3. **성찰 3문항을 교수에게 그대로 보여줄까** — 익명 처리할지, 이름과 함께 볼지.
4. **대회 심사 기준 원문** — 공고문에 'AI 리터러시'가 어떻게 정의돼 있는지 확인되면 지표를 거기 맞춰 조정한다.
