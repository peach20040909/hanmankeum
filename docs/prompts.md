## 0. 이 문서가 밝히는 것

한만큼은 생성형 AI(Claude)를 **두 군데**에서 씁니다.

| 구분 | 어디에 | 무엇을 |
|---|---|---|
| **서비스 안** | 교수 평가기준 정리 · 기록 분류 · 기여 요약 · 자기 기술 초안 | 이 문서 2~4장에 프롬프트 전문 |
| **서비스를 만들 때** | 코드 작성 | 이 문서 9장, 검증 기록은 `docs/ai-review.md` |

여기 적힌 프롬프트는 **실제로 배포본에서 돌아가는 문자열 그대로**입니다. 발표용으로 다듬은 게 아닙니다. 원본 위치를 장마다 표시했습니다.

**핵심 입장 한 줄.** 프롬프트를 잘 쓰는 것으로는 부족합니다. AI는 지시를 어기고, 없는 걸 지어내고, 하지 말라는 평가를 합니다. 그래서 **프롬프트로 한 번, 서버 코드로 또 한 번** 막습니다. 5장이 그 설계입니다.

## 1. 공통 설정

네 프롬프트 모두 같은 호출 구조입니다 (`ai.js` · `askJSON()` 한 곳에서 호출).

| 항목 | 값 | 왜 |
|---|---|---|
| 모델 | `claude-haiku-5-5` (환경변수 `HANMANKEUM_MODEL`로 변경) | 분류·정리는 큰 모델이 필요한 일이 아니고, 학기 내내 돌아가므로 비용이 낮은 모델을 씁니다 |
| 출력 형식 | `json_schema` (구조화 출력) | 자유 텍스트를 파싱하면 형식이 깨질 때마다 다르게 실패합니다. 스키마로 고정하면 **서버가 검증할 수 있는 모양**으로 옵니다 |
| `stop_reason` | `end_turn`이 아니면 **결과를 버리고** 규칙으로 대체 | 길이 초과로 잘린 JSON을 억지로 복구하지 않습니다 |
| 사용자 메시지 | 기록의 **제목·메타데이터 + 길이를 제한한 설명문 일부**(200자/160자) | 6장 |
| 호출 방식 | Anthropic Messages API `messages.create` + `output_config.format` | 공식 문서의 구조화 출력 방식 그대로. 시간 제한 45초, 재시도 1회 |

### 1-1. 배포본 연결 상태 (2026-11-10 연결)

본선 초안까지는 크레딧 문제로 API 키를 넣지 않아, 배포 사이트의 AI 기능이 **전부 규칙으로만** 돌고 있었습니다. 팀 피드백("AI가 하는 일이 코딩과 뭐가 다르냐")을 받고 실제로 연결했습니다.

| 항목 | 내용 |
|---|---|
| 연결 | Vercel 환경변수 `ANTHROPIC_API_KEY` (Secret 유형 — 저장 후 다시 볼 수 없음) |
| 모델 | `claude-haiku-5-5` |
| 비용 통제 | Claude Console 조직 월 지출 한도 US$5 (저장된 설정 화면 확인, 2026-11-10) · 충전 크레딧 US$5 · 키 만료 30일 |
| 확인 방법 | 착수 설정 화면에 "현재 연결된 모델: claude-haiku-5-5" 표시. 키가 없거나 호출이 실패하면 "AI 키 미연결 — 규칙으로 동작 중"으로 바뀌고, 결과마다 `AI`/`규칙` 출처가 붙습니다 |
| 실측 | 평가기준 정리 1회 약 6.7초 · GitHub 기록 75건 수집·분류 약 34초 · 요약 6~13초 · 자기 기술 초안 약 10초 |

**배포본에서 실제로 확인한 범위 (2026-11-10, 점검용 팀을 만들어 실행 후 삭제)**

| 기능 | 결과 | 비고 |
|---|---|---|
| 교수 평가기준 정리 | 18회 모두 AI 응답 | 8장 ④의 v1·v2 비교 |
| GitHub 기록 분류 | 75건 모두 AI 분류 · 확인 필요 9건 · 기준 밖 35건 | 기준 밖이 많은 문제는 8장 ⑤ |
| 직접 추가한 기록 분류 | AI·규칙 같은 항목 | "요구사항 명세서 v2 작성" → 요구사항 분석 및 설계 문서 |
| 기여 요약 | 수정 전 7회 중 3회 실패 → 수정 후 5회 모두 AI | 실패 원인과 수정은 8장 ⑤ |
| 자기 기술 초안 | AI 생성, 근거 표시 포함 | 1회 실행 |
| Notion 기록 분류 | **실측 성공 (2026-11-11)** | 새 교수 기준 점검 팀에서 실제 편집 → 웹훅 수신 → 팀원 자동 매칭 → Claude 분류 → 화면 표시. 아래 상세 |

**Notion 실제 이벤트 점검 (2026-11-11)**

- 점검 팀: 교수 기준 "자료·문서 작성 60% / 검토·오류 수정 40% / 최종 발표 태도는 기록 평가에서 제외"를 Claude가 정리(`criteria-draft-v2`)하고 교수 화면에서 수정·확정, 점검용 학생 2명 확인 후 잠금
- 다른 팀과 겹치지 않는 독립 점검 페이지("요구사항 명세서")를 만들고 사람이 본문을 직접 편집
- 처음에는 페이지의 Notion 연결이 '연결 없음'이라 기록이 오지 않았음 → 연결을 다시 허용한 뒤 기록 1건 수신 (11:31, 문서 편집)
- 결과: **자료·문서 작성**으로 분류, 출처 Claude(`criteria-classify-v1`), 규칙 판단도 같은 항목
- Claude 근거: "작업 기록이 요구사항 명세서에 대한 Notion 문서 편집이므로 자료·문서 작성 항목에 해당합니다."
- 참고: 기준 도입 전(고정 3축) 팀에서도 실제 편집 1건이 Claude로 분류되는 것을 확인했지만, 새 교수 기준 검증으로는 세지 않음

**팀원 자동 매칭 (같은 날 추가 점검)** — 점검 팀원에 실제 Notion 이메일을 등록한 뒤 새 페이지를 만들고 본문을 편집했습니다. 생성·편집 기록 2건이 모두 작성자를 손으로 지정하지 않고 '점검 사용자'로 자동 연결됐습니다. 직접 편집한 기록(11:45)은 자료·문서 작성으로 분류됐고, 출처는 Claude(`criteria-classify-v1`)이며 규칙 판단도 같았습니다.

**확인한 범위:** 새 교수 기준에서 실제 Notion 편집 → 웹훅 수신 → 팀원 자동 매칭 → Claude 분류 → 화면 표시. 아직 실측하지 않은 것:

- [x] Notion 작성자 → 팀원 자동 매칭
- [ ] 실제 `페이지 생성` 이벤트의 분류 결과 (수신·매칭은 확인했지만 분류 항목은 따로 기록하지 않음)
- [ ] 실제 외부 이벤트로 `남의 문서 편집` (자동 테스트로만 확인)
- [ ] 실제 Notion 이벤트가 두 번째 항목이나 '기준 밖'으로 분류되는 경우

자동 테스트는 외부 Notion 조회를 가짜로 바꾸고 실제 규칙 분류·DB 저장·잘못된 서명 거부를 검증한다. 이 결과는 실제 Notion 이벤트나 배포본의 AI 분류 성공을 증명하지 않는다.

**API 키는 저장소·문서·화면 어디에도 남기지 않습니다.** 코드는 환경변수 이름만 알고, 프론트엔드에는 연결 여부와 모델 이름만 내려보냅니다.

## 2. 프롬프트 ① 교수 평가기준 정리 — `criteria-draft-v2`

**목적** 교수님이 강의계획서·과제 안내문에 원래 쓰던 평가기준(자유 서술)을 받아, **협업 기록으로 확인할 수 있는 항목**(이름·설명·가중치·키워드·활동 종류)으로 정리합니다. 기록으로 확인할 수 없는 기준은 따로 빼서 이유와 함께 돌려줍니다.
**원본** `collect.js` · `draftCriteria()` · 화면: 착수 설정 3단계

**왜 이렇게 바꿨나.** 예선·초기 본선안은 서비스가 정한 고정 3축(MRL: 만들기·다듬기·이끌기)을 썼습니다. 팀 피드백에서 "축 정의가 끼워 맞춘 느낌이고, 근거 연구를 대지 못하면 질문에 방어가 안 된다", "교수님이 쓰려면 원래 쓰던 기준을 넣게 해야 한다"는 지적이 나왔습니다. 그래서 **기준은 교수님 것을 그대로 쓰고, AI는 그 기준을 기록에 적용할 수 있는 모양으로 옮기는 일**만 맡깁니다.

### 시스템 프롬프트 (전문)

```
대학 교수가 팀 프로젝트에 원래 쓰던 평가기준을 읽고, 협업 도구(GitHub·Notion) 작업 기록으로 확인할 수 있는 기여 항목으로 정리합니다.
규칙:
- 교수가 쓴 항목 이름과 표현을 최대한 그대로 씁니다. 새 이론이나 틀을 만들지 않습니다.
- 교수가 비율을 적었으면 그 비율을 weight로 옮기고, 없으면 비슷하게 나눕니다. 합계는 100입니다.
- 항목은 2~6개. desc는 어떤 작업 기록이 이 항목에 해당하는지 한 문장으로 씁니다.
- keywords는 이 항목의 작업 기록 제목에 실제로 나올 법한 짧은 단어(한국어·영어)를 3~8개 씁니다. PR·merge·commit처럼 모든 기록에 공통으로 나오는 말과, 특정 기능 이름(로그인 등)은 쓰지 않습니다.
- kinds는 이 항목에만 뚜렷하게 해당하는 활동 종류를 주어진 목록에서만 고릅니다. Commit·문서 편집처럼 여러 항목에 걸치는 종류는 넣지 않습니다. 해당이 없으면 빈 배열입니다.
- 작업 기록으로 확인할 수 없는 기준(발표 태도, 최종 결과물 품질, 출석, 오프라인 회의 참여 등)은 criteria에 넣지 말고 excluded에 원문과 이유를 적습니다. 이런 부분은 자기 기술·동료평가·교수 직접 평가로 확인합니다.
- 한국어로 씁니다.

활동 종류 목록: Commit, Pull request, 코드 리뷰, 리뷰 댓글, Issue, 페이지 생성, 문서 편집, 남의 문서 편집, 속성 편집, 댓글, 문서 작성
```

사용자 메시지는 `교수의 평가기준:\n<교수님이 붙여 넣은 원문>` 하나입니다(최대 4,000자).

### 출력 스키마

```json
{ "criteria": [ { "name": "기능 구현", "desc": "요구사항을 실제로 동작하는 기능으로 구현한 작업", "weight": 40,
                  "keywords": ["구현", "기능", "feat"], "kinds": ["Pull request"] } ],
  "excluded": [ { "text": "최종 발표 및 시연", "why": "발표·시연의 완성도는 작업 기록으로 확인할 수 없어 교수가 직접 평가" } ] }
```

`kinds`는 스키마의 `enum`으로 묶어, 목록에 없는 활동 종류를 지어낼 수 없게 했습니다.

### 이 프롬프트를 믿지 않는 장치

- **저장하지 않고 초안으로만 돌려줍니다.** 교수님이 화면에서 이름·가중치·설명·키워드·활동 종류를 고친 뒤 **기준 확정**을 눌러야 저장됩니다. 화면에 "원문과 다르게 옮긴 곳이 없는지 확인해 주세요"를 띄웁니다.
- **서버가 다시 정리합니다** (`normalizeCriteria`). 항목 6개 초과 버림, 이름 20자·설명 120자 자름, 목록 밖 활동 종류 제거, AI 초안의 가중치 합이 100이 아니면 비율을 유지해 100으로 맞춤. 교수님이 확정할 때는 같은 함수를 **엄격 모드**로 돌려 합 100·이름 중복을 오류로 막습니다.
- **어디서 왔는지 남깁니다.** 팀에 `criteria_meta`(AI 정리/규칙 정리/직접 입력, 프롬프트 버전, 교수 수정 여부, 제외한 기준)를 저장하고 리포트에 "AI 정리 → 교수 확정"으로 표시합니다. 교수님 원문도 함께 저장해 "산출 기준 보기"에서 열람할 수 있습니다.
- **AI를 쓸 수 없을 때** — `'항목 40%'`·`'항목 (30점)'` 형식의 줄만 규칙으로 읽어 초안을 만들고, 화면에 "규칙으로 읽은 초안"이라고 밝힙니다. 그 형식이 아니면 직접 입력을 안내합니다.

## 2-2. 프롬프트 ② 기록 분류 — `criteria-classify-v1`

**목적** 수집한 작업 기록 하나하나를 **교수님이 확정한 기준 항목** 중 하나에 연결하고, 그 이유를 한 문장으로 남깁니다. 어느 항목에도 맞지 않으면 `-1`(기준 밖)로 둡니다.
**원본** `collect.js` · `classify()`

### 시스템 프롬프트 (전문 · 기준 부분은 팀마다 교수 기준으로 채워짐)

```
대학 팀 프로젝트의 작업 기록을 교수가 정한 평가기준 항목 중 하나로 분류합니다. 평가가 아니라 분류만 합니다. 학생의 능력이나 성실성을 판단하지 마세요.
어느 항목에도 해당하지 않으면 type을 -1로 둡니다. reason은 한국어 한 문장으로, 기록의 어떤 부분을 근거로 그 항목에 연결했는지(또는 왜 해당이 없는지) 적습니다.

교수 기준 (인덱스: 이름 — 설명):
0: 기능 구현 — 요구사항을 실제로 동작하는 기능으로 구현한 작업 (예: 구현, 기능, 엔드포인트, feat, add)
1: 품질 관리 — 테스트·코드 리뷰·버그와 보안 수정으로 결과물을 고친 작업 (예: 수정, fix, 테스트, …)
…
```

### 사용자 메시지 형식

```
작업 기록:
0. [GitHub Pull request] AI 리터러시: 분류 교차 확인, AI 사용 표시, 프롬프트 버전 — AI 분류와 규칙 판단이 다르면 …
1. [GitHub Commit] 보안 검토 지적 6건 조치 + 검증 기록 문서화 — 독립 검토자에게 전체 코드베이스를 넘겨 …
2. [GitHub Commit] chore: Vercel 미리보기 배포 트리거 — …
```

한 번에 묶어 보냅니다(최대 80건). 기록마다 따로 호출하면 **같은 종류의 기록이 다르게 분류될 수** 있습니다.

### 출력 스키마

```json
{ "items": [ { "i": 0, "type": 0, "reason": "새 기능을 구현해 올린 PR이라 '기능 구현'에 연결했습니다." } ] }
```

### 설계 의도

- **"평가가 아니라 분류만 합니다"를 첫 문장에 둔 이유** — 분류를 시키면 모델은 자연스럽게 "이 학생은 기여가 많다"로 넘어갑니다. 평가 도구에서 가장 위험한 미끄러짐이라 맨 앞에서 막습니다.
- **`reason`을 반드시 받는 이유** — 이유를 못 쓰면 교수님이 검토할 수 없습니다. "AI가 그렇게 분류했다"는 근거가 아닙니다.
- **기준 설명과 키워드를 함께 넣는 이유** — 항목 이름만 주면 모델마다 다르게 해석합니다. 교수님이 확정한 설명·키워드로 해석 폭을 좁힙니다.
- **`-1`(기준 밖)을 허용하는 이유** — 억지로 어딘가에 넣으면 점수가 부풀습니다. 맞는 항목이 없는 기록은 점수에서 빼고 교수님이 볼 수 있게 남깁니다.
- **인덱스로 받는 이유** — 항목 이름을 문자열로 받으면 미세하게 어긋난 값이 옵니다. 범위 밖 인덱스는 서버가 버리고 규칙 분류로 대체합니다.

### 이 프롬프트를 믿지 않는 장치

같은 기록을 **규칙 분류기도 동시에** 분류합니다(`ruleClassify`). 규칙은 **교수님이 확정한** 활동 종류(일치 +2)와 키워드(하나당 +1)로 점수를 매겨 가장 높은 항목을 고르고, 아무것도 맞지 않으면 판단을 보류합니다. 즉 교차 확인의 기준선도 서비스가 아니라 교수님 기준입니다.

```
AI 분류 ─┐
         ├─ 같으면 → 분류 일치 (정확성을 보증하지 않음)
규칙 분류 ┘         다르면 → 확인 필요 → 교수가 원본을 보고 확정
```

**'일치'는 두 방식이 같은 답을 냈다는 뜻일 뿐, 그 답이 맞다는 뜻이 아닙니다.**
둘이 같이 틀릴 수 있습니다. 그래서 화면도 "아래만 확인하시면 됩니다"가 아니라
**"불일치 기록부터 검토하세요. 일치한 기록도 일부는 표본으로 확인하시는 편이 안전합니다"**라고 씁니다.

**교수가 확정하기 전까지 `확인 필요` 뱃지는 사라지지 않습니다.** 리포트 PDF에도 "교수님이 확인할 기록" 쪽으로 따로 빠집니다.

> **아직 증명하지 못한 것** — "규칙으로도 나눌 수 있으면 왜 AI를 쓰는가"는 정당한 질문입니다. 지금 우리에게는 **사람이 확인한 표본을 기준으로 AI 단독 · 규칙 단독 · 교차 확인 세 방식을 비교한 측정값이 없습니다.** 그래서 이 문서는 AI가 규칙보다 정확하다고 주장하지 않습니다. 교차 확인을 두는 이유는 정확도가 아니라 **두 판단이 갈리는 지점을 드러내 사람에게 넘기기 위해서**입니다. 실측 비교는 다음 학기 실증의 과제로 남겨 둡니다.

또한 분류에 쓰는 재료는 기록의 **제목과 짧은 설명문**이지 작업 전체의 맥락이 아닙니다. 분류 정확도의 상한이 거기서 정해집니다.

## 3. 프롬프트 ③ 기여 요약 — `summary-v1`

**목적** 한 학생의 기록 묶음을 읽고 3~5문장으로 요약합니다. **문장마다 근거 기록 번호를 함께** 내놓게 합니다.
**원본** `generate.js` · `SUMMARY_SYSTEM`

### 시스템 프롬프트 (전문)

```
대학 팀 프로젝트에서 한 학생의 작업 기록을 읽고, 그 학생이 한 일을 3~5문장으로 요약합니다.
규칙:
- 모든 문장은 반드시 근거가 된 기록 번호를 refs에 넣습니다. 기록에서 직접 확인되는 사실만 씁니다.
- 학생의 능력·성실성·태도를 평가하지 않습니다. "열심히", "뛰어난", "성실하게" 같은 표현을 쓰지 않습니다.
- 기록에 없는 일, 결과물의 품질, 다른 팀원과의 비교는 쓰지 않습니다.
- [AI 도움 표시]가 있는 기록은 "AI 도움 표시가 있다"고 사실대로 밝힙니다.
- 3인칭 평서문("~했다")으로, 한국어로 씁니다. 문장 안에 번호를 적지 말고 refs에만 넣습니다.
```

### 사용자 메시지 형식

```
학생: 박준호 (역할: 팀장 · 개발)
작업 기록:
[1] (GitHub Pull request, 2026-10-16, 기능 구현) AI 리터러시: 분류 교차 확인, AI 사용 표시, 프롬프트 버전 — … [AI 도움 표시]
[2] (GitHub Commit, 2026-10-31, 기능 구현) Notion 연결 점검 엔드포인트 추가 — … [AI 도움 표시]
[3] (GitHub Commit, 2026-10-30, 프로젝트 관리) chore: Other 프리셋으로 재배포 — … [AI 도움 표시]
```

`[n]` 번호는 **이 요청 안에서만 쓰는 임시 번호**입니다. 실제 DB id는 보내지 않습니다. 응답을 받은 뒤 서버가 번호 → id로 바꿉니다.

### 출력 스키마

```json
{ "sentences": [ { "text": "AI 분류 교차 확인과 Notion 연결 점검 기능을 구현했다.", "refs": [1, 2] } ] }
```

### 설계 의도

- **`refs`를 문장 안이 아니라 별도 필드로 받는 이유** — 문장 안에 `[1]`을 쓰게 하면 서버가 정규식으로 긁어내야 하고, 모델이 형식을 흘리면 검증이 통째로 무력해집니다. 분리하면 **번호가 없는 문장은 자동으로 걸러집니다.**
- **"다른 팀원과의 비교는 쓰지 않습니다"** — 비교는 한 사람의 기록만으로 할 수 없는 말인데, 요약 모델은 쉽게 넘어갑니다.
- **AI 도움 표시를 밝히게 한 이유** — AI 사용은 감점 요소가 아닙니다. **숨기는 게 문제**입니다. 그래서 모델에 "사실대로 밝혀라"라고 지시합니다.

## 4. 프롬프트 ④ 자기 기술 초안 — `selfdraft-v2`

**목적** 학생이 자기 기술을 백지에서 쓰지 않도록, 본인 기록만으로 3~6문장 초안을 만듭니다. **학생이 고쳐 쓰는 출발점**이지 제출본이 아닙니다.
**원본** `generate.js` · `DRAFT_SYSTEM`

### 시스템 프롬프트 (전문)

```
대학 팀 프로젝트를 마친 학생이 자기 기술을 쓸 수 있도록, 본인의 작업 기록만으로 초안을 3~6문장 씁니다.
규칙:
- 1인칭("저는 ~했습니다")으로 씁니다. 학생이 고쳐 쓸 출발점일 뿐입니다.
- 모든 문장은 근거 기록 번호를 refs에 넣고, 기록에서 확인되는 사실만 씁니다.
- 자기 자랑이나 능력·태도 평가("열심히", "주도적으로 뛰어나게")를 넣지 않습니다.
- 기록에 없는 오프라인 활동은 지어내지 않습니다. 쓸 사실이 모자라면 문장 수를 줄입니다.
- [AI 도움 표시]가 있는 기록은 AI 도움을 받았다고 밝힙니다.
- 문장 안에 번호를 적지 말고 refs에만 넣습니다.
```

사용자 메시지와 출력 스키마는 ②와 같습니다.

### 설계 의도

- **"학생이 고쳐 쓸 출발점일 뿐입니다"를 프롬프트에 넣은 이유** — 완성도를 올리라는 압력을 빼기 위해서입니다. 초안이 너무 잘 쓰여 있으면 학생이 그대로 냅니다. 그러면 자기 기술의 의미가 사라집니다.
- **"기록에 없는 오프라인 활동은 지어내지 않습니다"** — 이게 자기 기술의 유일한 위험 지점입니다. 오프라인 기여(회의 진행, 장비 준비)는 로그에 안 남는데, 모델은 그럴듯하게 채워 넣습니다.
- **수정률을 따로 잰다** — 초안과 학생 최종본을 문장 단위로 비교해 **그대로 / 고침 / 새로 씀 / 지움**과 전체 수정률(%)을 리포트에 표시합니다(`compareDraft`). 수정률이 0%면 교수님이 그 사실을 봅니다.
- **수정률은 점수가 아닙니다** — 많이 고쳤다고 깊이 검토한 것도, 적게 고쳤다고 성찰하지 않은 것도 아닙니다. 초안을 어떻게 썼는지 보여주는 **참고 정보**일 뿐이며, 학습 성찰의 깊이나 기여 수준을 재는 지표로 쓰지 않습니다. 기여율에도 반영하지 않습니다.

## 5. AI를 믿지 않기 위한 서버 검증

**프롬프트의 주요 제약을 서버에서도 한 번 더 점검합니다.** 프롬프트는 부탁이고, 코드는 강제입니다.

다만 서버가 확인하는 것은 **형식**입니다 — 인용 번호가 실재하는지, 금지 표현이 섞였는지, 문장과 기록이 글자 수준에서 겹치는지. **문장이 사실인지는 기계가 확정하지 못합니다.** 그래서 확정할 수 없는 것은 지우지 않고 사람에게 넘깁니다.

| 검사 | 하는 일 | 어긴 문장은 |
|---|---|---|
| **근거 번호 존재 검사** | `refs`의 번호가 실제 보낸 기록 범위 안인지 | **전부** 없는 번호면 문장째 제외, 이유 공개 |
| **일부만 틀린 경우** | 유효한 번호가 하나라도 있는지 | 문장은 **살리고** 유효한 근거만 연결, `없는 번호 N는 제외함`을 함께 표시 |
| **근거 없음 검사** | `refs`가 비었는지 | 제외 |
| **평가 표현 차단** | 정규식 `JUDGE`로 성실·능력·열심·뛰어·우수·훌륭·탁월·부족·태만·무임승차·소극·적극적으로·주도적·책임감·노력했·헌신·"기여도가 높/낮" 탐지 | 제외 |
| **약한 연결 표시** | 문장과 인용 기록의 2글자 조각 겹침이 0.12 미만 | 지우지 않고 **`연결 약함`으로 표시** |

**걸러진 문장은 조용히 버리지 않습니다.** 교수 화면과 리포트에 "제외된 문장과 이유"로 남습니다. AI가 무엇을 틀렸는지가 보여야 AI를 검토할 수 있습니다.

> **한 줄로 정리하면** — 근거 번호가 실재한다고 해서 그 문장이 사실인 것은 아닙니다. 서버는 *근거가 붙어 있는지*까지만 보증하고, *근거가 맞는지*는 교수님이 원본을 열어 확인합니다. 화면도 `근거 확인 통과`가 아니라 **`근거 ID 연결 검사 통과`**라고 씁니다.

> 왜 '약한 연결'은 지우지 않고 표시만 하는가 — 2글자 겹침은 형태소 분석 없이 쓰는 거친 지표라, 맞는 문장을 잘못 걸러낼 수 있습니다. **기계가 확신할 수 없으면 사람에게 넘깁니다.** 확인 필요 장치와 같은 원칙입니다.

### AI를 못 쓸 때

API 키가 없거나 호출이 실패하면 **규칙으로 전환하고 화면에 그렇게 표시합니다**(`규칙 문장 · AI 미연결`). 조용히 품질이 떨어지는 대신, 지금 무엇이 돌고 있는지를 보여줍니다.

## 6. AI에 보내는 것과 보내지 않는 것

| | GitHub | Notion |
|---|---|---|
| **수집·저장** | 제목, 작성자, 시각, 원본 URL + 작성자가 직접 쓴 **설명문**(커밋 메시지 · PR/이슈 본문 · 코드 리뷰 댓글, 최대 4,000자) | 이벤트의 페이지 ID, 편집자, 시각, 변경 블록 수 + 페이지 제목·URL(토큰으로 조회) |
| **AI에 전달** | 제목 + 설명문의 **앞부분만** (분류 200자 · 요약 160자) | 제목과 메타데이터 |
| **수집하지 않음** | **코드 본문 · diff · 파일 내용** | **문서 본문 · 댓글 내용 · 대화** |

AI에는 기록의 제목과 메타데이터를 중심으로 보내고, 작성자가 쓴 설명문은 길이를 잘라 일부만 포함합니다.
**코드 diff와 Notion 문서 본문·댓글은 수집 단계에서부터 제외합니다** — 보내지 않는 게 아니라 애초에 가져오지 않습니다.

## 7. 프롬프트 버전 관리

프롬프트를 고치면 버전 문자열을 올리고, **기록마다 어떤 버전으로 분류됐는지 DB에 남깁니다**.

| 버전 | 쓰는 곳 |
|---|---|
| `criteria-draft-v2` | 교수 평가기준 정리 (v1 → v2: 8장 ④ 검수·비교 반영) |
| `criteria-classify-v1` | 기록 분류 |
| `summary-v1` | 기여 요약 |
| `selfdraft-v2` | 자기 기술 초안 |

```
records.prompt_version  ← 이 기록은 어느 프롬프트로 분류됐나
                          규칙으로 분류된 기록은 null
```

**왜 남기나.** 학기 중에 프롬프트를 고치면 앞뒤 기록이 다른 기준으로 분류됩니다. 버전이 없으면 나중에 그 사실조차 알 수 없습니다. 학생이 이의를 제기했을 때 **"이 기록은 v1으로 분류됐다"**를 확인할 수 있어야 합니다.

분류 프롬프트는 예선의 5유형 분류 → 본선 초안의 고정 3축(`mrl-3axis-v2`) → 교수 기준 분류(`criteria-classify-v1`)로 바뀌었습니다. 고정 축을 없앤 이유는 2장에 적었습니다.

## 8. 프롬프트 검수 기록

제출 전 프롬프트를 처음부터 다시 읽고 고친 내역, 그리고 배포본에서 실제로 돌려 본 출력을 검수한 기록입니다. **고친 내역을 남기는 것까지가 프롬프트 관리**라고 봤습니다.

**① `selfdraft` — 뜻이 통하지 않는 지시 (수정)**

```
(이전) 기록에 없는 오프라인 활동은 지어내지 않습니다. 대신 마지막 문장 없이 끝냅니다.
(이후) 기록에 없는 오프라인 활동은 지어내지 않습니다. 쓸 사실이 모자라면 문장 수를 줄입니다.
```

"마지막 문장 없이 끝냅니다"는 쓴 사람만 아는 말이었습니다. 모델 입장에서는 해석이 안 되는 지시이고, 해석 안 되는 지시는 **무시되거나 엉뚱하게 따릅니다.** 의도(없으면 억지로 채우지 마라)를 그대로 적었습니다. → `selfdraft-v1` → **`selfdraft-v2`**

**② 프롬프트 금지어와 서버 차단 목록 불일치 (수정)**

`selfdraft` 프롬프트는 "주도적으로"를 금지 예시로 들고 있는데, 서버의 `JUDGE` 정규식에는 `주도적`이 없었습니다. **프롬프트가 막는 표현을 코드가 안 막으면 이중 방어가 한 겹**이 됩니다. 정규식에 추가했습니다.

**③ 분류 프롬프트에 "애매하면 어떻게 하라"가 없음 (예선 3축 버전에서 보류 → `criteria-classify-v1`에서 일부 해결)**

3축 버전에는 어느 축에도 또렷하게 안 붙는 기록을 만났을 때 모델이 어떻게 할지 지시가 없었습니다. 교수 기준 버전에서는 **맞는 항목이 없으면 `-1`(기준 밖)로 두라**는 출구를 만들어, 억지로 끼워 넣는 문제는 줄였습니다. 아래 문단은 그 전의 판단 기록이고, "확신이 낮을 때"의 처리는 여전히 같은 이유로 남은 과제입니다.

교차 확인이 **일부는** 걸러 줍니다 — AI와 규칙이 갈리면 `확인 필요`로 올라오니까요. 하지만 **둘이 같이 틀리면 그대로 통과합니다.** 그래서 "피해가 없다"고는 말할 수 없고, **지금 그 크기를 모른다**고 말하는 쪽이 정확합니다.

고친다면 "확신이 없으면 가장 보수적인 축을 고르고 reason에 그렇게 적어라"가 될 텐데, 이건 분류 분포 자체를 바꿉니다. **사람이 직접 분류한 기준 데이터 없이 바꾸면 좋아졌는지 나빠졌는지도 알 수 없어**, 이번 제출본에서는 고치지 않았습니다. 다음 학기 실증에서 기준 데이터를 만든 뒤 검증하고 바꿀 계획입니다.

> 고치지 않기로 한 판단도 기록에 남깁니다. **무엇을 확인했는지가 무엇을 고쳤는지만큼 중요합니다.**

**④ `criteria-draft-v1` 실제 출력 검수 (2026-11-10, 배포본에서 실행)**

입력한 교수 기준 (예시 과목):

```
소프트웨어공학 팀 프로젝트 평가
- 요구사항 분석 및 설계 문서 20%
- 기능 구현 50%
- 테스트와 코드 리뷰 20%
- 협업(회의록, 일정 관리) 10%
- 최종 발표는 별도 평가
```

Claude(`claude-haiku-5-5`)가 돌려준 초안 요약:

| 항목 | 가중치 | 키워드 (AI 제안) | 활동 종류 (AI 제안) |
|---|---|---|---|
| 요구사항 분석 및 설계 문서 | 20 | 요구사항, 명세서, 설계, 분석, 유스케이스, ERD, 아키텍처, SRS | 문서 작성 |
| 기능 구현 | 50 | 구현, 기능, feature, API, 로그인, PR, merge, 구현완료 | Pull request |
| 테스트와 코드 리뷰 | 20 | 테스트, test, 리뷰, review, 단위테스트, 버그, 검증, QA | 코드 리뷰, 리뷰 댓글 |
| 협업(회의록, 일정 관리) | 10 | 회의록, 회의, 일정, 스프린트, 마일스톤, 담당자, 마감, 주간보고 | 페이지 생성, 속성 편집 |

제외: "최종 발표는 별도 평가" — *발표는 협업 도구에 남는 작업 기록이 아니고 교수가 별도로 평가하므로 제외. 발표 준비 과정은 자기 기술이나 교수 직접 평가로 확인.*

**잘한 것** — 교수 원문의 항목 이름과 비율을 그대로 옮겼고(새 틀을 만들지 않음), 기록으로 확인할 수 없는 "발표"를 스스로 빼고 이유를 달았습니다. 프롬프트가 요구한 대로입니다.

**교수가 고쳐야 할 것 (그래서 초안을 바로 저장하지 않습니다)**
- `PR`, `merge`는 모든 PR 제목·머지 커밋에 붙는 말이라 **아무 기록이나 '기능 구현'으로 끌어당기는 키워드**입니다. 규칙 교차 확인의 기준선이 흐려집니다 → 삭제 권장.
- `로그인`은 이 과목의 특정 기능 이름이지 항목을 가르는 말이 아닙니다. 다른 팀에는 맞지 않습니다 → 삭제 권장.
- `버그`가 '테스트와 코드 리뷰'에 들어갔는데, 버그 **수정**을 구현으로 볼지 리뷰로 볼지는 교수님 판단입니다. AI가 정할 일이 아닙니다.
- '요구사항 분석 및 설계 문서'의 활동 종류가 `문서 작성`(수동 링크 기록)뿐이라, Notion에서 만든 설계 페이지(`페이지 생성`)는 규칙으로 잡히지 않습니다. 반대로 `페이지 생성`은 '협업'에 들어가 있어 설계 문서 페이지가 협업으로 끌려갈 수 있습니다 → 교수님이 어느 쪽에 둘지 정해야 합니다.

**프롬프트 수정 (→ `criteria-draft-v2`)** — 첫째·둘째 문제는 프롬프트로 줄일 수 있어 keywords 규칙에 한 줄을 더했습니다: *"PR·merge·commit처럼 모든 기록에 공통으로 나오는 말과, 특정 기능 이름(로그인 등)은 쓰지 않습니다."* 다만 나머지 둘은 **프롬프트로 없앨 문제가 아니라 교수님이 판단할 문제**라서, 화면에서 "원문과 다르게 옮긴 곳이 없는지 확인하고 고쳐 주세요"를 띄우고 초안을 저장하지 않는 설계를 유지합니다.

**v1 · v2 같은 입력 비교 (2026-11-10, 배포본)**

수정이 실제로 효과가 있었는지 보려고, 성격이 다른 교수 기준 3개를 v1과 v2에 **각각 3번씩** 넣었습니다(총 18회). 같은 입력이라도 출력이 매번 조금씩 달라서 한 번만 비교하면 우연을 개선으로 착각할 수 있기 때문입니다.

| 입력한 교수 기준 | 공통 단어 키워드 (PR·merge·머지·수정 등) v1 → v2 | 특정 기능 이름 키워드 (로그인·게시판·회원가입·화면 등) v1 → v2 |
|---|---|---|
| ① 소프트웨어공학 (비율 명시, 발표 별도) | 0 → 0 | 7 → 0 |
| ② 웹프로그래밍 (로그인·게시판 등 문장형) | 8 → 0 | 9 → 0 |
| ③ 경영전략 (코딩 아님, 발표 태도 10%) | 2 → 2 | 0 → 0 |
| **합계 (각 9회)** | **10 → 2** | **16 → 0** |

- 항목 이름·가중치는 v1·v2 모두 교수 원문과 같았고, 발표·시연은 9회 모두 제외로 분리됐습니다. 즉 v2는 **좋던 부분을 해치지 않고** 문제 키워드만 줄였습니다.
- **남은 것** — ③에서 v2도 `수정`을 2번 넣었습니다. "보고서 작성 및 편집" 항목이라 아주 틀린 말은 아니지만, 범용 단어라 규칙 기준선을 흐릴 수 있습니다.
- **대가** — ②의 "GitHub 이슈·PR 기반 협업"처럼 교수 기준 자체가 PR을 말하는 경우에도 v2는 `PR` 키워드를 빼서, 그 항목의 규칙 매칭이 약해집니다. 이 경우 교수님이 확정 단계에서 키워드를 직접 넣어야 합니다.
- ③에서 발표 태도 10%를 제외하자 나머지 30·40·20이 **33·44·23으로 다시 맞춰졌습니다**(합 100 유지). 의도한 동작이지만 교수님이 원문 비율과 다르다는 걸 알아야 하므로, 화면에서 확정 전에 보이게 둡니다.
- 3회씩은 작은 표본입니다. "줄었다"는 이 입력들에서 확인한 것이고, 모든 교수 기준에서 같다는 보장은 아닙니다.

**⑤ 실동작 점검에서 나온 문제 (2026-11-10)**

1. **요약이 간헐적으로 규칙 문장으로 대체됨 (수정)** — 기록 76건인 학생의 요약을 7번 만들었더니 3번이 규칙 문장이 됐습니다. 그런데 화면에는 "AI 미연결"로만 보여 원인을 알 수 없었습니다. 먼저 **실패 사유를 저장·표시하도록** 고친 뒤 다시 돌려 원인(`AI 응답 중단: max_tokens` — 근거 번호 목록이 길어 출력 한도 3,000토큰을 넘김)을 찾았고, 한도를 8,000토큰으로 올렸습니다. 수정 후 5번 모두 AI로 생성됐습니다. 잘린 JSON을 억지로 복구하지 않는 원칙은 그대로입니다.
2. **기준 밖이 47% (고치지 않음 · 교수 판단 필요)** — 이 저장소 기록 75건 중 35건(전부 Commit)이 '기준 밖'이 됐습니다. 대부분 "화면 스타일 수정", "넘치던 이름 줄바꿈" 같은 **버그·화면 수정**인데, 입력한 기준에 그런 항목이 없어 AI가 어디에도 넣지 않았습니다. 억지로 넣지 말라는 프롬프트대로 동작한 것이지만, 교수님 입장에서는 "버그 수정은 구현에 넣는다"처럼 정하고 싶을 수 있습니다. 프롬프트를 "가장 가까운 항목을 고르라"로 바꾸면 기준 밖은 줄지만 억지 분류가 늘어납니다. 그래서 프롬프트를 바꾸지 않고, **교수님이 기준 설명(desc)에 포함 범위를 적도록** 안내하는 쪽을 택했습니다. 기준 밖 기록은 리포트에서 개수와 함께 보이고 교수님이 하나씩 옮길 수 있습니다.

## 9. 개발 과정에서의 생성형 AI 사용 (출처 표기)

| 도구 | 용도 |
|---|---|
| **Claude (Anthropic)** — Claude Code | 서비스 코드 작성, 리팩터링, 테스트 작성 |
| **Claude** (Anthropic) — 별도 세션 | 작성에 참여하지 않은 **독립 검토자**로서 전체 코드 보안 검토 |
| **GPT-6 ASTRA** (OpenAI) — 별도 세션 | 같은 코드베이스를 다시 점검 · 완성된 서비스를 **"사용자의 눈"으로 점검**해 피드백 13건 |

코드는 AI와 함께 썼습니다. 숨길 일이 아니라 밝힐 일입니다. 다만 **"AI로 만들었다"는 말만으로는 아무것도 보증하지 못합니다.** 그 결과를 어떻게 검증했는가가 중요합니다.

작성자가 자기 코드의 빈틈을 못 보기 때문에, 코드를 쓰지 않은 **별도 AI 검토자**에게 전체 코드베이스를 넘겼습니다. 7건이 보고됐고, **사람이 하나씩 재현해 확인한 뒤** 고쳤습니다. 그중 하나는 **기여율을 직접 조작할 수 있는 취약점**이었습니다(이메일 검증이 `%@%`를 통과시켜 SQL `LIKE` 와일드카드로 팀의 미매칭 기록을 전부 가로챌 수 있었음).

이건 우리 서비스의 `확인 필요` 장치와 같은 발상입니다. **만든 쪽과 검토하는 쪽을 분리합니다.**

전체 내역: [`docs/ai-review.md`](./ai-review.md)

### 다른 회사 모델에게도 같은 코드를 맡겼습니다

같은 회사 모델끼리는 같은 맹점을 공유할 수 있습니다. 그래서 개발에 쓴 모델과 **다른 회사 모델(GPT-6 ASTRA, OpenAI)**에게도 같은 코드베이스를 넘겨, 다른 관점에서 한 번 더 찾게 했습니다.

**이 과정이 취약점이 없다는 보증은 아닙니다.** 모델이 둘이어도 같은 것을 함께 놓칠 수 있고, 두 검토 모두 전문 보안 감사가 아닙니다. 할 수 있는 말은 여기까지입니다 — **AI가 낸 지적을 그대로 받지 않고, 사람이 하나씩 재현해 확인한 뒤 고쳤습니다.**

### 완성된 서비스는 "사용자의 눈"으로 한 번 더 봤습니다

코드의 결함과 **평가 도구로서의 결함**은 다른 종류입니다. 그래서 다 만든 서비스를 GPT-6 ASTRA에게 "이걸 실제로 쓰는 교수와 학생이라면 어디서 막히겠는가"로 다시 보게 했습니다. 13건이 돌아왔고, 그중 먼저 고쳐야 할 것으로 꼽힌 5건은 이렇습니다.

| 받은 피드백 |
|---|
| AI가 쓴 문장과 규칙으로 만든 문장의 표시가 한 화면에서 엇갈린다 |
| "원본을 열어 확인하세요"라고 해놓고 원본 링크가 없는 기록이 있다 |
| **AI와 규칙이 같다고 해서 맞는 건 아닌데**, 화면이 그렇게 읽힌다 |
| 확인할 기록이 남았는데 기여율을 "산출 완료"로 보여준다 |
| **"근거 확인 통과"는 인용 번호가 실재하는지 본 것일 뿐**, 내용이 사실인지 본 게 아니다 |

**한 건씩 사람이 직접 화면에서 재현해 보고, 반영할지 말지를 정했습니다.** 이 과정 자체가 우리 서비스가 교수님께 요구하는 것과 같은 모양입니다 — AI가 낸 지적을 그대로 받지 않고, 근거를 확인하고 판단은 사람이 합니다.

## 10. 앞으로 — 학교 LMS 연동 (이번 범위 밖)

프롬프트 설계와 직접 관련은 없지만, 분류 품질에 영향을 주므로 적어 둡니다.

지금은 교수가 팀과 팀원을 손으로 등록합니다. LMS와 연동되면 수강생 명단·팀 편성·과목 정보가 자동으로 들어오고, **분류 프롬프트에 과목 맥락(예: 개발 중심 / 기획 중심)을 넣을 수 있습니다.** 같은 "회의록 작성"도 과목에 따라 비중이 다릅니다.

LMS 연동은 **학교 기관 승인이 필요해 학생 팀이 자체적으로 권한을 받을 수 없어** 이번 범위에서 제외했습니다. 단계는 ① 명단 CSV 일괄 등록 → ② LTI 1.3 연동 → ③ SSO·성적 화면 첨부입니다.
