# AI가 쓴 코드를 사람이 검증한 기록

2026-11-01

## 왜 이 문서가 있나

한만큼의 코드는 **AI(Claude)와 함께 작성했습니다.** 숨길 일이 아니라 밝힐 일입니다. 다만 "AI로 만들었다"는 말만으로는 아무것도 보증하지 못합니다. 중요한 건 **그 결과를 어떻게 검증했는가**입니다.

이 문서는 그 검증 과정과 결과를 남긴 것입니다. 우리 서비스가 교수님께 "AI 분류를 그대로 믿지 말고 근거를 확인하세요"라고 말하는 것과 같은 원칙을, 우리 코드에도 적용했습니다.

## 어떻게 검증했나

| 수단 | 무엇을 잡는가 |
|---|---|
| 자동 테스트 12개 (`npm test`) | 권한, 산식, 분류 규칙, 근거 검증, 웹훅 서명 — 매 변경마다 실행 |
| 독립 보안 검토 (2중) | 코드를 쓰지 않은 **별도 AI 검토자 둘** — Claude(Anthropic) · GPT-6 ASTRA(OpenAI) — 에게 전체 코드베이스를 넘겨 취약점 탐색 |
| 사람의 판단 | 검토자가 올린 지적을 하나씩 재현·확인하고, 고칠 것과 받아들일 것을 결정 |
| 운영 환경 확인 | 배포 후 실제 요청으로 권한 거부·용량 한도·서명 검증을 직접 호출해 확인 |

**검토자를 분리한 이유**는 작성자가 자기 코드의 빈틈을 보지 못하기 때문입니다. 한 걸음 더 가서 **서로 다른 회사의 모델 둘**에게 따로 맡겼습니다. 코드를 쓴 모델과 검토한 모델이 같으면 같은 맹점을 공유할 수 있기 때문입니다. 이건 우리 서비스의 `확인 필요` 장치(AI 분류 ≠ 규칙 분류일 때 사람에게 넘김)와 같은 발상입니다 — **판단이 갈리는 지점을 사람에게 넘기려면, 판단하는 쪽이 둘 이상이어야 합니다.**

## 2026-11-01 보안 검토 결과

전체 코드(약 2,230줄)를 대상으로 했습니다. 6건이 보고됐고, **제가 하나씩 재현해 확인한 뒤** 조치했습니다.

### 고친 것

**① 와일드카드 이메일로 남의 기록 가로채기 (HIGH)** — `handler.js`

Notion 이메일 검증이 `/^[^\s@]+@[^\s@]+$/`였습니다. 이 정규식은 `%@%`를 **통과시킵니다.** 그 값이 SQL의 `LIKE` 패턴에 그대로 들어가고 있었습니다.

```js
// 이전
"... AND lower(login) LIKE ?", mid, id, `%<${email}>`
```

`%`는 LIKE 와일드카드라서, 학생이 자기 이메일을 `%@%`로 저장하면 패턴이 `%<%@%>`가 되어 **팀의 미매칭 Notion 기록 전부**가 본인에게 붙습니다. 기여율은 기록 수로 계산되므로 숫자가 직접 조작됩니다. 평가 도구에서 가장 나쁜 종류의 결함입니다.

조치: `%` `_`를 거부하도록 검증을 조이고, LIKE를 버리고 **정확 일치**로 바꿨습니다. 재발 방지 테스트를 추가했습니다.

**② 같은 이메일을 두 사람이 등록 (MEDIUM)** — 팀원 A가 팀원 B의 Notion 이메일을 등록하면 B의 기록이 A에게 갔습니다. 팀 안에서 이메일 중복을 막았습니다(409).

**③ 초대 키가 주소에 노출 (MEDIUM)** — 첨부 파일 링크가 `?k=<초대키>` 형태였습니다. 이 키는 이 시스템의 **유일한 자격증명**인데, 주소창·브라우저 기록·서버 접근 로그에 남습니다. 우리는 다른 곳에서는 일부러 키를 주소에서 지우고 있었는데(`#/join/...` 처리), 첨부 링크가 그걸 되돌리고 있었습니다. `X-Key` 헤더로 받아 blob으로 여는 방식으로 바꿨습니다.

**④ 웹훅 검증 토큰이 로그에 평문 (MEDIUM)** — 이 토큰이 곧 서명 비밀키입니다. 로그 접근 권한만 있으면 위조 서명을 만들어 가짜 기록을 넣을 수 있습니다. 기본은 앞 10자 지문만 남기고, 최초 설정 때만 `NOTION_SETUP_LOG=1`로 전체를 출력하게 했습니다.

**⑤ 남의 Notion 페이지 등록 (MEDIUM)** — 다른 팀이 이미 등록한 페이지를 가로챌 수 있었습니다. 중복 등록을 막았습니다(409).

**⑥ `__proto__` 를 배열 인덱스로 (LOW)** — 이의 제기 API가 `sentences[b.index]`에 사용자 값을 그대로 썼습니다. `{"index":"__proto__"}`로 `Array.prototype`을 오염시킬 수 있었습니다. 정수·범위 검사를 넣었습니다.

**⑦ 저장소 이름의 `..` (검토자 신뢰도 6, 그래도 조치)** — `owner/name` 검증이 `..`를 허용해 GitHub API 경로를 벗어날 여지가 있었습니다. 한 줄로 막았습니다.

### 문제없다고 확인한 것

검토자가 "이상 없음"으로 보고한 항목도 함께 남깁니다. 무엇을 **확인했는지**가 무엇을 고쳤는지만큼 중요합니다.

- **XSS** — 화면이 문자열 템플릿으로 HTML을 만들지만, 서버에서 온 값은 모두 `esc()`를 거칩니다. 속성·URL 자리까지 하나씩 추적해 빠진 곳이 없음을 확인했습니다.
- **SQL 인젝션** — 모든 질의가 `?` 바인딩입니다. 식별자를 문자열로 붙이는 곳은 `db.js`의 마이그레이션 한 곳뿐이고, 값은 코드에 하드코딩된 배열에서만 옵니다.
- **웹훅 서명** — 원본 바이트로 HMAC을 계산하고 `timingSafeEqual`로 비교하며, 헤더나 비밀키가 없으면 거부합니다.
- **첨부 권한** — 파일 → 자기 기술 → 팀 순으로 소유 팀을 거슬러 확인하고, 학생은 본인 첨부만 열 수 있습니다.
- **정적 파일 경로 탈출** — 허용 목록 방식이라 요청 경로가 파일 경로에 섞이지 않습니다.
- **권한 누락** — 모든 라우트가 `authorize`를 먼저 호출하고, 교수 전용·학생 전용 구분이 빠진 곳이 없습니다.

## 발표에서 쓸 한 줄

> AI가 쓴 코드에서 **기여율을 직접 조작할 수 있는 취약점**이 나왔고, **다른 회사 모델을 포함한 독립 검토자 둘**이 찾아 사람이 확인하고 고쳤습니다. AI를 썼다는 사실보다, 그 결과를 검증할 수 있는 절차를 갖췄다는 점이 중요합니다.
